# CodeAgent —— 简易代码智能体

调研开源 Claude Code 类项目的实现机制后，实现的一个**简易代码智能体**：
输入两份架构文档（`Architecture_Documentation.md` + `Architecture_View.md`），
自动生成一个**完整、可运行的项目**（目录结构、代码、依赖声明、README、测试用例、Dockerfile）。

底层模型：**DeepSeek `deepseek-v4-pro`**（官方 API，无需本地部署权重）。

## 快速开始

### 方式一：Windows 桌面版（推荐，无需 Python）

1. 双击 `dist/CodeAgent.exe`（目标机器无需预装任何环境）。
2. 在界面中：
   - 填写 **DeepSeek API Key**（仅保存在内存，不落盘；也可用环境变量 `DEEPSEEK_API_KEY`）；
   - 选择**架构文档**与**架构视图**两个输入文件；
   - 选择**输出目录**；
   - 点击 **启动 Agent**。
3. 观察日志：`预检 → 解析 → 计划 → 生成 → 检查 → 修复 → 完成`。
4. 完成后可一键打开输出目录，按生成的 `README.md` 运行项目。

### 方式二：命令行（开发者）

```bash
# 真实 API（Key 取环境变量）
python -m codeagent --doc <架构文档.md> --views <架构视图.md> --out <输出目录>

# 离线 Mock 联调（无 Key）
python -m codeagent --mock --doc <架构文档.md> --views <架构视图.md> --out <输出目录>

# 跳过生成后的运行时验证（离线/无 Node 环境）
python -m codeagent --no-verify --doc <架构文档.md> --views <架构视图.md> --out <输出目录>
```

运行测试：

```bash
python -m unittest discover -s tests -v
```

## 实现机制（调研结论落地）

参考仓库：`ultraworkers/claw-code`（Rust 版 Claude Code 类实现）、
`Windy3f3f3f3f/how-claude-code-works`（Claude Code 架构分析）以及 Claude Code 公开资料。
详见 [调研记录.md](调研记录.md)。

| 机制 | 本实现 |
| --- | --- |
| Agent 循环 | 循环调 LLM → 提取 tool_calls → 逐个执行 → 结果作为 `role=tool` 消息回填 → 继续；步数上限 + 可取消 |
| 接口分层 | `LLMClient` / `ToolExecutor` 两个最小协议，真实客户端与 Mock 客户端可互换（同 claw-code 的 `ApiClient`/`ToolExecutor` trait 设计） |
| 上下文管理 | 静态 system 提示词 + 动态数据（spec digest / plan / manifest）放 user 消息；原始 Markdown 不直接进 LLM，预处理为结构化 JSON 摘要（8-12KB） |
| 状态机 | `Preflight → Preprocess → Plan → Generate → CheckGate → RepairLoop(≤2) → Finalize` |
| 检查与自修复 | 静态检查（齐全性/语法/JSON/依赖/SQL 建表覆盖）+ **运行时验证闸门**：真实执行 `npm install` + `npm test`，失败摘要反馈进修复循环（离线环境自动跳过）；修复轮 ≤2 |
| 推理型模型适配 | Plan 阶段开 `thinking` + JSON 输出模式；工具调用阶段显式 `thinking: disabled`（否则 temperature 无效且回传 reasoning_content 会 400） |
| 错误处理 | 401/402/429 区分处理；网络错误与 5xx 指数退避重试；计划校验失败重试 1 次后落入确定性兜底计划 |
| 安全 | 写路径强制工作区内相对路径；run_check 按 argv 解析 + 白名单命令形态 + `shell=False`（模型输出字符串绝不进 Shell）；单文件/总量写入上限；`npm install --ignore-scripts`（不执行生成内容中的生命周期脚本）；子进程超时整树终止；Key 不落盘 |

## 输入 / 输出规范

**输入**：任务书指定的两份架构文档。`Architecture_Documentation.md` 会被预处理为结构化
JSON（章节/表格/代码块/追溯矩阵/组件/技术选型/交付物），`Architecture_View.md` 的
PlantUML 图会被解析为元素/关系/流程结构；预处理阶段还会**确定性检测文档自身矛盾**
（如交付物文件名不一致），并把检测结果一并交给模型。

**输出**（写入指定目录）：

每次任务会在所选输出目录下创建**独立子目录** `generated_<时间戳>/`，
绝不移动或删除用户已有的文件（输入文件与输出目录重叠也安全）。

| 要求 | 保证方式 |
| --- | --- |
| 项目目录结构 + 完整代码文件 | Plan 阶段产出文件清单（3-50 个，校验通过才执行），Generate 阶段逐个写入 |
| 依赖声明 requirements.txt / package.json | 计划校验**强制**包含 |
| Dockerfile（选做） | 计划提示词要求按需包含 |
| 项目 README | 计划校验**强制**包含 README.md（含数据库初始化步骤与架构简化说明） |
| 配套测试用例 | 计划校验**强制**包含 tests/ 下至少一个测试文件 |
| 交付物覆盖 | 架构文档交付物清单中的每个文件必须出现在计划中 |
| 功能覆盖 | 架构文档描述浏览器/界面功能时，计划**强制**包含前端文件（html/jsx/vue/css 或 public/static/frontend 目录），不得只生成后端 API |
| 数据库完整性 | 检查器核对 SQL DDL 的 CREATE TABLE 与代码中的表引用（FROM/INTO/UPDATE/JOIN），缺表即报错进入修复循环 |

另写入 `project_plan.json`（第 4 步产物）与 `run_report.json`（运行报告：停止原因、
模型调用次数、tokens、遗留问题、**verification 字段**——运行时验证执行情况如实记录：
`passed` 通过 / `failed` 失败 / `skipped` 未执行（含原因）/ `not_run`）。

## 离线自检与隔离启动验证

在 PowerShell 中运行：

```powershell
.\acceptance\run_offline_acceptance.ps1
```

脚本复制 exe 和两份架构文件到独立目录，只将子进程 PATH 设置为 Windows
System32，并清除该子进程的 Python 路径和 API Key。系统环境变量不变。
exe 通过显式的 `--offline-self-test` 参数启用自检：填写测试输入、勾选 Mock、
调用界面的启动按钮，保存生成结果、界面日志、截图与 `acceptance_result.json`。
自检不会调用真实 API。普通双击仍进入交互界面。

通过标准包括：运行于打包程序、外部 python/py/node/npm 均不可查找、任务完成、
代码和依赖声明及 README 和测试文件齐全、运行时验证跳过情况如实记录。
这是当前电脑上的隔离启动验证，不能代替全新 Windows 系统的兼容性验证。

## 提交前修复记录（2026-11-10 终审六项；2026-11-11 复核新增第 7 项）

针对终审意见的六项修复（第 1–6 条）与完成后复核新增的一项（第 7 条），
全部有单测覆盖：

1. **数据库完整性**：checker 新增规则——SQL DDL 的 CREATE TABLE 必须覆盖代码引用的
   所有表（实测缺陷：样例 user.js 用 users 表但 DDL 只有 games/questions，mock 测试
   发现不了）；提示词要求 README 含数据库初始化命令；验收阶段用真实 PostgreSQL
   走通注册/登录/答题/查分流程。
2. **输出目录**：每次任务在所选目录下创建 `generated_<时间戳>/` 独立子目录，不再
   移动用户已有文件（修复"输入文件在输出目录内被先移走再读失败"）；并防御性检查
   输入文件不得位于本次工作区内。
3. **run_check 白名单**：改为 shlex 按 argv 解析 + argv[0] 查白名单 + 参数形态校验 +
   拒绝 shell 元字符 + `shell=False` 直接 exec，模型输出的整段字符串不再进 Shell
   （修复 `node --check a.js & 其他命令` 注入洞）。
4. **打包后的 Python 检查**：`getattr(sys, "frozen", False)` 区分源码/exe 运行；
   打包版下 python/py 检查改用系统 PATH 上的解释器，找不到时返回明确错误说明
   （打包版可独立完成 node --check / npm test；Python 检查需源码运行）。
5. **检查状态分离**：`run_report.json` 新增 `verification` 字段，检查通过/失败/未执行
   三种状态分开记录；跳过（无 node/npm、离线等）不再冒充"测试全部通过"，完成
   结论如实标注"运行时验证未执行（原因）"。
6. **UI 功能覆盖与架构简化**：预处理器检测文档是否描述浏览器/界面功能
   （介绍/主菜单/答题/结束反馈等），计划校验强制前端文件；提示词要求把微服务等
   架构简化记录到计划 notes 与生成项目的 README「Architecture decisions」；
   计划文件上限 40 → 50（容纳前端文件）。
7. **完成结论由程序生成**（2026-11-11 复核新增）：修复前完成消息直接采用模型
   complete 摘要，探针实测出现 "All tests passed；运行时验证未执行" 的自相矛盾
   文案。现在结论一律由程序按真实验证状态生成——只有真实执行 npm test 且全部
   通过才出现"运行时验证通过"，未执行/跳过时如实标注原因；模型摘要经剥离
   验证类语句后仅作为"生成内容"附注，绝不参与通过/失败结论。
